

    Завдання 1: Автоматизація та скриптинг

     1. Які процеси найчастіше автоматизуються і чому?

Найчастіше автоматизуються рутинні, повторювані та критичні до помилок процеси:

    CI/CD (Інтеграція та доставка):   Збірка коду, запуск тестів та деплой.  Чому:  Щоб виключити людський фактор і пришвидшити релізи.
    Управління інфраструктурою (IaC):   Створення серверів, мереж та баз даних.  Чому:  Для ідентичності середовищ (Dev/Staging/Prod).
    Моніторинг та оповіщення:   Перевірка стану систем.  Чому:  Для миттєвої реакції на збої без участі людини 24/7.
    Безпека (DevSecOps):   Сканування коду на вразливості.  Чому:  Для виявлення дірок у захисті на ранніх етапах.

     2. Як оцінити ефективність автоматизації? Ключові показники (DORA metrics):

    Deployment Frequency (Частота деплоїв):   Як часто код потрапляє в продакшн.
    Lead Time for Changes (Час виконання змін):   Час від написання коду до його запуску.
    Change Failure Rate (Коефіцієнт відмов):   Відсоток деплоїв, що призвели до збоїв.
    Mean Time to Recovery (MTTR - Середній час відновлення):   Як швидко система повертається до ладу після інциденту.

     3. Bash vs Python: різниця та застосування

    Bash (Shell):  
   Різниця:  Це командна оболонка. Працює безпосередньо з системними утилітами.
   Задачі:  Прості системні скрипти, обгортки (wrappers) для команд Linux, однорядкові операції з файлами, налаштування оточення всередині Docker-контейнерів.


    Python:  
   Різниця:  Повноцінна мова програмування з багатими бібліотеками.
   Задачі:  Складна автоматизація, робота з API хмарних провайдерів (AWS/Azure), обробка даних (JSON/YAML), написання тестів, створення інструментів моніторингу.



     4. Найкращі практики для масштабування автоматизації:

    Модульність:   Розподіл скриптів на дрібні компоненти, які можна перевикористовувати.
    Версіонування:   Зберігання всієї автоматизації в Git.
    Idempotency (Ідемпотентність):   Скрипт має працювати так, щоб повторний запуск не ламав систему, а приводив її до потрібного стану.
    Документація та самодокументований код.

    Завдання 2: Інфраструктура як код (IaC) та Terraform

     1. Декларативний та імперативний підходи

    Імперативний (Як робити):   Ви пишете послідовність команд. Наприклад: "Створи сервер -> Встанови Nginx -> Відкрий порт 80". (Приклад: Bash, CLI).
    Декларативний (Що отримати):   Ви описуєте кінцевий результат. "Мені потрібен 1 сервер з Nginx". Система сама вирішує, як це зробити. (Приклад: Terraform, Kubernetes).

     2. Категорії IaC інструментів:

    Infrastructure Provisioning:   Створення базової інфраструктури (Terraform, CloudFormation).
    Configuration Management:   Налаштування ОС всередині серверів (Ansible, Chef, Puppet).
    Container Orchestration:   Управління контейнерами (Kubernetes, Docker Swarm).

     3. Основні команди Terraform:

1. `terraform init` — ініціалізація робочої директорії та завантаження плагінів (provider).
2. `terraform plan` — попередній перегляд змін (що буде створено/змінено/видалено).
3. `terraform apply` — виконання змін та створення реальних ресурсів.
4. `terraform destroy` — видалення всієї інфраструктури, описаної в проекті.

     4. Різниця між Provider та Resource у Terraform:

    Provider:   Це "перекладач" між Terraform та API хмарного сервісу (наприклад, AWS, Google Cloud, Azure). Він каже Terraform, як спілкуватися з хмарою.
    Resource:   Це конкретний компонент інфраструктури, який ви хочете створити (наприклад, віртуальна машина `aws_instance`, база даних або мережа).

     5. Популярні патерни використання Terraform:

    Terraform + Ansible:   Terraform створює "залізо" (сервер), а Ansible встановлює на нього софт.  Перевага:  Гнучкість у налаштуванні ОС.
    Terraform + CI/CD (GitOps):   Запуск Terraform через Jenkins або GitHub Actions.  Перевага:  Кожна зміна в інфраструктурі проходить аудит та автоматичну перевірку.
    Modular Infrastructure:   Використання модулів для різних середовищ (Dev/Prod).  Перевага:  Швидке розгортання ідентичних середовищ для тестування.
